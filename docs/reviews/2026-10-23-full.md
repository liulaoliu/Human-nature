# 全库审查（性能 / 架构 / 功能）

- **日期**：2026-10-23
- **范围**：`src/**`、`server/**`、`tools/**`（A–G 七维度）
- **基线**：commit `0d9f65e`，工作区干净
- **门禁**：`tsc -b` 绿；246 个测试文件 / 2315 passed / 1 skipped；架构 R1–R8 绿；上帝文件 0 新增
- **超 600 行的文件**：`ReaderApp.tsx` 747、`useStudySession.ts` 695、`sqliteStore.js` 667（都低于 800 门禁线）
- **数据规模**：词库 8709 条 / 16.3MB；`xueba.db` 53MB；`data/backups` **753MB**；`public/tts` 32MB；`dist` 49MB

## 一、结论

功能面已经比较完整（精读工作流、AI 跑批、闭卷拷打、离线 TTS 都通了）。**这轮最值得动的不是加功能，而是「词库全量写放大」**：

> 点一次「加入生词本」＝ 客户端 `JSON.stringify` **116ms** → PUT **16.3MB** →
> 服务端再 `stringify` **121ms** → **两次 `gzipSync`（各 277ms）** → 重建投影表。
> 同步阻塞 Node 主线程 **≈ 0.7–1s**。

这个成本随词库条数**线性增长**，而词库只增不减。它同时拖慢三件事：加词手感、dev/静态服务的其他请求（同进程单线程）、每日备份体积。

## 三、已经做得好的（这轮别动）

- **数据安全**：读失败不写、覆盖前留上一版、快照 gzip + 保留 5 版、`close()` 截断 WAL、版本冲突 409 不降级——这套是踩过事故换来的，别为了性能随手简化。
- **AI 跑批**：待办不再 `slice(0,30)`、回执数真实写入、重跑要确认、进度按「问过」算。
- **同源校验**：所有能写/能发网络请求的接口都过了 `allowLocalRequest`。
- **门禁**：R1–R8 + 上帝文件 + 架构检查都在跑，新增违规会被拦。

## 四、重构路线（每步可单独提交、可单独回滚）

1. **写合并**（P1-1 前半）：`persist` 加 300ms 尾触发合并 + `beforeunload`/`visibilitychange` flush。验收：连点 10 个词，只发 1 次 PUT；`useVocabLibrary.test` 补「合并/尾触发/卸载 flush」三条。
2. **服务端别重复压缩**（P1-1 后半 + P1-2）：`vocab_prev` 存 packed 结果；`gzipSync` → 异步 `gzip`。验收：`sqliteStore.test` 加「连续保存两次，第二次不再压 prev」。
3. **快照降频**（P1-1 ③）：按时间/条数节流。验收：模拟 20 次保存，快照数 ≤ 设计值。
4. **读路径瘦身**（P2-1 + P2-2）：先加 `GET /api/store/vocab?view=light`，前端首屏用它；`contexts/examples` 改为按需。验收：首屏载荷 < 5MB；`vocabRepo` 加「light 视图缺字段时不崩」测试。
